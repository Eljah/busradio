# Архитектура и инварианты

## Три независимых контура

```text
Браузер администратора
       │ HTTPS + HttpOnly session + CSRF
       ▼
Java-сервер: редакторы → FFmpeg → PCM CAS → подписанная публикация
       │                      ▲
       │ ночной Wi-Fi         │ подтверждённые события + heartbeat
       ▼                      │
Edge: download.part → SHA-256 → атомарный active.json
       │
       ├── GPSD / свежий локальный buscrawl JSONL
       ├── определение направления → геовыбор → частотные ограничения
       └── музыка / окно рекламы → непрерывный PCM
                                      │
                       null / WAV / ALSA / native FM

Pi4J: подготовленный вход зажигания и индикатор состояния.
```

Публикация не выполняет команды ОС на борту и не управляет частотой передатчика. Частота, аппаратная конфигурация и разрешение на RF задаются только локально. Нативный бинарник никогда не приходит в пакете плейлиста. ProcessBuilder вызывается без shell и без командных строк из рекламного контента.

## Публикация и кеш

Сервер сохраняет редактируемые сущности отдельно от опубликованного пакета. Ревизии монотонны `r-000000000001`, `r-000000000002` и т.д. Релиз адресован конкретному `busId`, подписан Ed25519. Подпись проверяется по заранее установленному публичному ключу, не по ключу, пришедшему с тем же сетевым ответом.

Манифест содержит плейлист, прямое направление, альтернативное обратное, кампании и полный список необходимых PCM-объектов. Направления объединяются по префиксу до последнего `:`, например `123:0` и `123:1`. Направление без двоеточия не объединяется с похожими ID. Геометрия и кампании доступны офлайн.

Клиент скачивает объект в `<sha256>.pcm.part`; `Range` возобновляет загрузку. Длина берётся из подписанного манифеста; SHA-256 проверяется после получения. Все файлы проверяются до замены `active.json` атомарным переименованием. При повреждении нового файла старый пакет остаётся активным. Кеш с утраченным файлом при перезапуске не считается готовым: исправление скачивается при следующей разрешённой связи.

Игрок фиксирует пакет на границе элемента плейлиста. Публикация не обрывает песню или уже начавшееся окно. Предыдущие файлы не удаляются автоматически, поэтому активный старый элемент не теряет PCM во время обновления. Лимит кеша и резерв свободного места приводят к отказу от новой активации, а не к удалению ещё используемой музыки. **Автоматической уборки старых объектов в v0.1 нет**; необходимо плановое обслуживание диска. Сервер также удерживает ранее опубликованные этому борту хеши в разрешённом наборе.

## Рекламное окно

Окно задаётся длительностью в целых секундах. Бюджет выражен в PCM-кадрах: `seconds × 22050`. Песня вне окна воспроизводится целиком. Для каждого ролика проверяются:

1. GPS не старше 15 секунд, не более чем на 2 секунды из будущего, заявленная точность не хуже 75 м.
2. При движении от 2 м/с направление определяется по курсу и ориентированной полилинии; на остановке сохраняется только ранее надёжно определённое направление. При неоднозначности — отказ от георекламы.
3. Попадание автобуса в коридор направления: 100 м для SHAPE, 250 м для STOP_CHORDS. Самопересечения с неоднозначной продольной координатой отбрасываются.
4. Объект в радиусе кампании и преимущественно впереди по маршруту; допуск позади 25 м учитывает погрешность GPS. ETA — оценка по текущей скорости, не модель пробок.
5. Кампания включена, действуют абсолютные даты и ежедневное окно, хватает времени до объекта и остатка окна для полного ролика.
6. Соблюдены лимиты повторов конкретного борта, а этот ролик ещё не выбран в данном окне.

Сортировка допустимых кампаний: приоритет по убыванию, затем расстояние вперёд по возрастанию, затем ID. При одинаковом приоритете выигрывает ближайший объект впереди. Трасса между остановками не знает реальную доступность объекта пешком, ограждения и сторону посадки. Для промышленного использования нужны дорожные shapes и привязка объектов к допустимым остановкам/направлениям.

Если кандидата нет, остаток заполняется FILLER либо тишиной. FILLER может быть обрезан, рекламный ролик — нет. При потере зажигания начатый элемент прерывается с ABORTED. Небольшие рампы по 5 мс уменьшают щелчки на границах PCM, но полноценного loudness-normalization/crossfade нет.

## События и ограничения повторов

Лимит резервируется на диске ДО начала ролика. При падении питания это может консервативно израсходовать показ, который не прозвучал целиком, зато перезапуск не обходит cooldown. Дневной лимит действует на конкретном борту в часовом поясе кампании, не на весь парк.

STARTED и COMPLETED/ABORTED имеют разные UUID и общий `playbackId`. Каждый сохраняется отдельным атомарным файлом в outbox. Сервер сначала fsync-ит строку журнала, затем возвращает подтверждённые UUID. Повтор HTTP-запроса после потери ответа безопасен: IDs дедуплицируются, включая перезапуск сервера. Неполная последняя строка после обрыва записи удаляется; повреждение завершённой строки — ошибка, не молчаливое исправление.

COMPLETED означает успешную передачу указанного числа PCM-кадров выбранному программному выходу. Это **не** измеренный FM-приём, аудитория или юридически достаточный рекламный proof-of-play. События не подписываются отдельным аппаратным ключом; доверенный борт с токеном способен сообщить произвольные события. WAV/null помечаются simulation.

## Безопасность и границы версии

Сессионная админка, CSRF, строгий Origin, CSP без inline-скриптов, DOM `textContent` для пользовательских строк; bearer-токен отдельный на борт, хранение его SHA-256 на сервере; HTTPS вне loopback; запрет HTTP redirects и проверка подписей. Импорт не загружает музыку с произвольных URL: FFmpeg читает локальный файл с ограничением протоколов file/pipe, времени процесса и длины результата.

Всё равно необходимы TLS-прокси, ограничение запросов, мониторинг диска, резервные копии и собственное тестирование. JDK HttpServer не предназначен в этой реализации для открытого интернета без прокси. Файловая БД — один писатель; нет HA, транзакций между несколькими серверами и многопользовательской модели ролей. Журнал и индекс дедупликации растут, их ротация/архивирование не автоматизированы.

Не реализованы: глобальный бюджет кампаний, биллинг, обновление JAR по сети, точная map-matching модель круговых маршрутов, расписание рейсов/смена разных номеров маршрутов автоматически, аудит смен админки, мониторинг реального приёмника, RDS/стерео, приоритет аварийной связи и штатных объявлений водителя. Номер маршрута борту назначает администратор; автоматически меняется только направление среди опубликованных полилиний.
